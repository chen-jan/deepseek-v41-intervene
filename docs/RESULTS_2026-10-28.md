# First GPU boots of the edit engine (28 Oct 2026)

**Status: passed on a follow-up check, not on the pre-written gates.** The first two boots failed several gates. A
third (retry) boot ran the old gates unchanged plus three retry gates (`docs/GATES.md`); two retry gates came out
inconclusive because their test edits were too small, and two follow-up checks then settled the main question (section
"Retry boot and follow-up checks" at the end). Validate with your own direction before relying on edited-arm results.

Hardware and software: one node, 4x NVIDIA B200 (183 GB each), 32 CPUs and 700 GiB of host memory for the job,
vLLM 0.31.0, torch 2.13.0+cu130, CUDA 13.0, TP4. Checkpoint `deepseek-ai/DeepSeek-V4.1-Flash-1017` on local NVMe.
Throughput: `vllm bench serve`, random 8,192-token prompts, 1,500 forced output tokens.

The cap fails because the effect on these decoded texts is only 0.006-0.19 (the positive control measures 5-8 on the
prompt text), so the cap is 10% of a small number. The `decode_effect` retry gate tests this with a medium arm.

**Arm reload (graph boot).** `r2_differs`, `r3_is_r1` and the shas pass. `r2_is_arm4` fails: arm 4 reloaded into
slot 8 vs arm 4 in its own slot gives median 0.389, p95 1.92, top-1 0.799, against a floor of 0.013. 17 of 80
requests needed a NaN retry. `r3_vs_r1` is 0.0060, at the floor.

**Arm isolation (eager boot).** Counters exact (including the n = 8 children; nothing edited on other arms, 0
invalid arms). 17 requests miss their own native floor: all 16 arm-4 requests (mixed vs alone, median of medians
0.436) and one sham request (median 0.00897 vs a floor of 0.00873, top-1 0.9489 vs 0.9604). Pooled, arm 0 is within
the floor. 22 of 64 requests needed a NaN retry, all batched.

Together with reload: an 8 sd add at output 26 gives teacher-forced distances of about 0.4 between two runs of the
*same* arm when batch composition differs. The sham floor does not cover that. The `repeat` retry gate measures the
arm's own repeat floor.

**Projection exact (eager boot).** The exact part passes at all 26 slots: 0 cast violations, 0 non-finite values,
stats `max_err` = capture `max_err`, capture positions = host positions. The sd rule fails at output 26:

| Arm | max err (sd) | q99.9 (sd) | frac <= 0.02 sd |
|---|---|---|---|
| 3 (project, all slots) | 0.714 | 0.0154 | 0.99985 |

At other slots (recorded, not gated) arm 3's maximum ranges from 0.29 to 26.3 sd (worst: output 31), while q99.9

the first suspect, but this was not verified; the `outliers` retry gate checks it.

## Retry boot and follow-up checks

Third boot: CUDA graphs, torch op, side stream on, same server code as the eager boot (stats fix included).

| Gate | Result |
|---|---|
| Install, build, sham, positive (all 8 paths) | PASS |
| Prefix cache | PASS (first measurement) |
| Decode, isolation, reload, projection (old rules) | FAIL again, as expected if the hypotheses hold |
| Outliers (retry) | PASS: every projection error above 0.05 sd sits on one first-position token with norm ~3e5, where the bf16 bound is ~256 sd; >= 99.985% of tokens within 0.02 sd |
| Repeat (retry) | FAIL. Strong arms (8 sd add): mixed-batch vs alone 0.433, own repeat 0.441, so within their own noise; shams next to them within the native floor; counters exact. But the weak arms (0.5 and 1 sd) moved logprobs by only 0.015 / 0.028 (< 10x the 0.013 floor), so small-edit leaks were untested |
| Decode effect (retry) | inconclusive: a 4 sd add changes its own decoded text by only 0.15-0.32, below the 0.5 the gate needs; one noise-bound miss (0.035 vs 0.025) |

**Follow-up 1: repeat and decode effect with 2 and 4 sd test edits** (`DSV41_WEAK_ADD_SD=2,4`; a follow-up, not the
pre-written rule). The 4 sd arm is sensitive (effect 0.57). Shams next to it stay within their floor and counters are
exact, but its own result in a mixed batch of 32 vs alone in a batch of 16 differs by 0.105, about 5x its repeat noise
(0.021). Decode effect is again inconclusive; its one noise-bound miss moved to a different path, so it looks random.

**Follow-up 2: batch size vs mixing** (`tools/batchcheck.py`; reading rule fixed before the run). Same 16 prompts,
batch size held at 32, only the neighbours' arm changes (all edited vs all sham):

| Prompts | Arm | Mixing only (fixed size) | Repeat noise | Batch size only (16 vs 32) | Edit kept in mixed batch | Reading |
|---|---|---|---|---|---|---|
| generic (median 1.7k tokens) | 4 sd add | 0.088 | 0.087-0.089 | 0.103 | 98.6% (q05 97.0%) | harmless rounding |
| generic | 8 sd add | 0.428 | 0.374-0.399 | 0.402 | 99.5% | harmless rounding |
| agent transcripts (median 17k tokens) | 4 sd add | 0.308 | 0.270-0.302 | 0.304 | 99.1% | harmless rounding |
| agent transcripts | 8 sd add | 0.291 | 0.288-0.298 | 0.295 | 99.8% | harmless rounding |

So the earlier mixed-vs-alone differences come from batch size (the GPU's reduction order), amplified by the edit, not
from mixing arms. Unedited requests show the same effect: batch size alone moves them by 0.0065 on short prompts and
0.097 on 17k-token transcripts. It applies equally to every arm in a randomized batch.

**Proxy:** PASS on this boot.
